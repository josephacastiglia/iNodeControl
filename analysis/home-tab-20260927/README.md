# Home inserts a Tab into an active text field: 27 Sep 2026

**Status: reproduced on the mock; cause traced; phone comparison prepared, not yet run.** No product code, kernel or setting was changed. The candidate is not promoted.

## Why Tab precedes Command+H

- **The kernel's Home is the vendor's Home, copied byte for byte.** `InputRouter` sends `fn_key == "Home"` as `Stroke(0, 43)` (Tab), then `Stroke(8, 11)` (Left GUI+H). The kernel self-test pins exactly that ("Home reproduces observed Tab and GUI+H sequence").
- **Source of the sequence.** On 14 Sep, IMService's `WriteFile` calls were observed with Frida (`analysis/HID-PROTOCOL.md`; raw data in `analysis/hid-keys-20260914.jsonl` with `hid-key-markers.jsonl` in the main checkout). Each of the three vendor Home presses in that capture was: release, `A2 00 2B` (Tab), release, `A2 08 0B` (GUI+H), release. AppSwitch and ControlBar start with the same Tab.
- **No record explains the Tab.** It was reproduced because it was observed, and the sequence arrived with the initial source import (`ee445d7`).
- **Context on C24C.** Full Keyboard Access is On, and its help lists Tab as "move forward" and Space as "activate". AppSwitch (flag `02` + Up) and ControlBar (flag `02` + C) match FKA's Fn+↑ and Fn+C commands. Command+H is a system shortcut, not an FKA command.
- **Hypotheses for the Tab (untested):**
  - (a) It wakes FKA's hidden focus ring, so a following FKA command is not swallowed. AppSwitch and ControlBar need that; Home may not.
  - (b) It is an unneeded vendor artefact.
- In a focused text field the Tab is typed. That was seen on 27 Sep 15:48, when it went into the test note.

## Reproducible test (mock)

Harness scenario **S9** (`tools/input-cleanup-harness`):
- It drives the console's own `ApiClient` against the real kernel code on a simulated board: Send text `ab`, then `fn_key=Home` (what the console's Home button sends), then `c`.
- It decodes the kernel's actual reports as a focused text field would receive them (`HidText`, built by inverting the kernel's `HidProtocol.Ascii`).

| Sequence | Field receives |
|---|---|
| `ab`, Home, `c` (current kernel) | `ab\t[GUI+h]c`: **Home types a Tab** |
| Home alone | `\t[GUI+h]` |
| AppSwitch | `\t[flag02+0x52]` (Tab too; not in scope) |
| ControlBar | `\t[flag02+c]` (Tab too; not in scope) |
| V1: Command+H only | `[GUI+h]` |
| V2: Command alone, then Command+H | `[GUI+h]` |

S9 also checks that replay V0 equals the kernel's Home reports byte for byte. S1–S9 all pass.

**What the mock cannot answer:** whether iOS goes Home on V1 or V2, including after idle with FKA's ring hidden, and whether anything else depends on the Tab. Only the phone can.

## Proposed phone test (needs a coordinated window; not run)

**How the variants reach C24C without restarting the rack.**
- The release kernel's own executable has a development mode, `iMouse2.Kernel.exe --hid-replay C24C <file>`. It writes a validated report sequence (keyboard and mouse families only) to one board and then releases keys and buttons.
- This leaves the running kernel and both AirPlay receivers untouched. Replacing the kernel instead would stop both receivers, because they are its child processes, and both phones would need mirroring re-selected.
- It does bypass the kernel's input ownership for C24C while it runs. Exclusivity comes instead from the candidate console holding C24C's lease, idle, during each replay. Keyboard reports do not change the kernel's pointer estimate. **Your explicit approval is needed for this path.**

**Before the window:**
- C24C's AirPlay mirroring has been offline since about 16:59. The phone needs to be unlocked and mirroring re-selected (Control Center, Screen Mirroring, iMouse2-C24C).
- You stop using the PC.

**Procedure, about 20 minutes, C24C only:**
1. Read-only preflight: processes and paths, C24C identity, leases, operator settings hash.
2. Close the installed console normally. Launch candidate `b0708e3` with isolated settings (`"trackPointer": false`), identified by PID, and let it take C24C's lease.
3. For each variant in the order V1, V2, V0 (control):
   - **(a) Text field.** In a new Notes note (Notes quick action, New Note), Send text `HomeTest`, then replay the variant. Record whether the phone went Home, and after reopening the note, whether a tab follows `HomeTest`.
   - **(b) No text field.** From a Settings list page, replay the variant and record whether it went Home.
   - **(c) After idle.** After 60 s with no input (FKA's ring hidden), from Settings, replay the variant and record whether the **first** press went Home.
   - Frames are captured read-only throughout. The console's Home button is not used during the test.
4. Restore: close the candidate, verify the lease is released, and relaunch the installed console without using it. The test notes stay and are documented.

**Decision rule.** A variant qualifies only if it goes Home in (a), (b) and (c) and leaves the note text unchanged. If V1 fails only after idle and V2 passes, hypothesis (a) holds and V2 is the fix. If neither passes, Home keeps its Tab, and the fix has to avoid focused fields another way. A kernel change comes only after the phone result, with S9 flipped to assert that no Tab is typed.
