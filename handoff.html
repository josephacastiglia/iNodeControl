iMouse 2.0

A Windows replacement console for iMouse XP International Edition — the vendor software driving a rack of iPhones. One phone shown large and live, every other phone as a tile beside it, and one phone's clicks and drags mirrored to all the rest.

Two independent channels, not one

This single fact explains most of the project's surprises, and it is the thing to hold onto.

Either path can fail while the other works perfectly. A phone can show a flawless picture and ignore every tap; a phone can accept every tap and show nothing.

So the console always reports control status and video status separately per phone. Any report of the form "phone X isn't working" must be split along this line before anything else.

Full detail with measurements is in analysis/HARDWARE.md — read it before touching anything timing- or protocol-related. It is the most valuable file in the repo.

How a frame reaches the screen

poll /pic/screenshot?binary=true       raw BMP, ~2 ms
 ├─ SameAsPrevious? → discard, poll again          ← most polls land here
 └─ LiveFrame.Prepare       on a worker thread     row-flip, optional downscale
     └─ Dispatcher.BeginInvoke(Render)             present now, not on the next tick
         └─ WriteableBitmap.WritePixels            one copy, no allocation

Two rules this path enforces, both learned the hard way:

  • Never derive the poll interval from measured frame gaps. It feeds back on itself — one missed frame widens the gap, which lengthens the sleep, which misses more. Measured decaying from 23 fps to 16.5.
  • Never present on CompositionTarget.Rendering. It fires on WPF's own schedule, so a frame arriving just after a tick waits up to 28 ms. Posting at Render priority on arrival took present-interval spread from 9.5 ms to 0.5 ms.

How an input reaches the phone

Every input endpoint accepts a comma-separated id list, so mirroring to N phones is one request, not N. InputTargetIds() returns master,follower1,follower2…; Followers() excludes phones that are offline, have no working board, or have a different screen size — an identical coordinate on a different-sized screen is not the same place.

A drag is a real /mouse/down → streamed /mouse/move → /mouse/up, run on the thread pool. It is not replayed as a canned swipe.

Phones are independent — there is no shared bottleneck

  • Two phones polled concurrently, flat out: 83 and 85 req/s, p50 3 ms — the same as either one alone.
  • Ten concurrent pollers: 512 req/s total, p50 3 ms.
  • Streaming /mouse/move while polling frames: 98.8 req/s, against 78.7 with no input traffic at all.

The board walks the pointer

Latency of one /mouse/move, by distance travelled
JumpOne phoneBoth phones
2 px1.0 ms1.0 ms
100 px78 ms77 ms
400 px250 ms242 ms
1000 px592 ms594 ms

Identical for one phone or ten — the board walks every phone in an id list in parallel. Three consequences:

  • A move's latency is meaningless without its distance. A p50 of 3.7 ms with a max of 264 ms looks like jitter; it is the distance distribution.
  • Coalescing a drag is free. Sending only the newest position skips no pixels — the board traverses the path either way. Verified: the same stroke as 14 steps, 7 steps and 2 jumps gave identical results on both phones.
  • A full-height swipe is slow by construction (~580 ms), and iOS may read it as a drag rather than a flick. Prefer the short axis.

Two identical iPhone XRs on the same iOS build. The second one's AirPlay stream is genuinely ~5× slower, and it is just as slow when it is the only phone being polled. This is not fixable in software — it is that phone's Wi-Fi link, and the vendor's own software hits the same wall. Each tile therefore shows its own live fps, so a slow phone reads as a slow phone and not a slow app.

Corrections

Beliefs this project held that measurement killed

Each of these was written down as fact at some point. Do not let them back in.

Refuted Wall thumbnails starve the master view

Recorded as "30 fps fell to 19.8 with a single tile running flat out", and it shaped the wall's whole design — a 1 fps throttle. That measurement was reading the source rate, not contention. A clean three-run A/B: 

wall off        master 17.7 fps   p50 31.9 ms   tiles  0.0 fps
wall at 30 fps  master 17.6 fps   p50 32.3 ms   tiles 11.8 fps

The wall is free. It no longer stands aside during drags either.

Refuted The iPhone pointer isn't carried in the AirPlay stream

It is. The frame-diff threshold used to look for it was simply too coarse.

Refuted ~5 fps were presented but never displayed

Measured drops were 0–1 per 8 s. The apparent loss was mistimed frames being scored as duplicates by a 30 Hz sampler — which cannot resolve a 30 Hz stream.

Traps

Do not re-enter these

Measurement Never compare screenshots byte-for-byte

A mirrored screen never repeats exactly — the clock, the AirPlay encoder and wallpaper parallax all move on their own. An MD5 comparison reports "reacted" for an untouched phone as reliably as for a tapped one. Use mean absolute pixel difference against an idle control: idle measures ~0.02, a real reaction 20–160.

Measurement Normalise phone state before comparing

Phones drift onto different home pages, and the two XRs in this rack have entirely different home screens and wallpapers — the same coordinate is Clock on one and Reminders on the other. Two Home presses first (one leaves the app, one returns to page one). Even then, a coordinate is only a fair probe if both phones have the same icon there.

Measurement Never probe with a state-dependent gesture

Watching for a home-page flip or an app to open is unreliable: a phone already on its last page, or an edge gesture iOS declines, is indistinguishable from mirroring having dropped that phone. Probe instead with what was sent — assert the delivered coordinate and id list — or where the pointer ended up, as mean pixel difference in a small box around the stroke's final coordinate. Measured 1.4–9.8 against an idle floor of 0.02. A whole-frame diff cannot see a dot a few pixels across; this is why auto-bind uses a box.

Hardware A phone can silently stop accepting taps

Measured: a phone took /mouse/move normally — the pointer visibly followed — but every /mouse/click did nothing, on its own and mirrored alike. /mouse/up did not fix it, so it is the pointer's own state, not a stuck button. Hardware keys kept working throughout, so the phone looks perfectly healthy. /mouse/reset clears it, permanently.

The console now resets the pointer across the whole target set whenever the mirror set changes. If a phone ever appears to be "skipped by mirroring", try Reset first.

Benchmarks Measurement hygiene

A still screen produces almost no new frames, so benchmarking one measures nothing — drive continuous motion, which is what --wall-test does. gdigrab captures whichever window is on top; one run read 0.1 fps because the vendor console was covering the app. A 30 Hz sampler cannot resolve a 30 Hz stream. This display is at 150% DPI.

--ui-test is the valuable one. TestHandler serves a five-device fixture (TEST:01…05) with deliberate variety: offline, no board, and one phone at a different screen size so mirroring exclusion can be asserted.

The gesture stages take a plain Point rather than a mouse event — BeginGesture, TrackGesture, EndGestureAsync — specifically so tests can drive the exact path a real press follows. Synthesising WPF mouse events is not practical.

Build and deploy

dotnet build src/iMouse.Console/iMouse.Console.csproj -c Release -o release/iMouse2-net

Then copy five files — iMouse2.exe, .dll, .deps.json, .runtimeconfig.json, .pdb — from release/iMouse2-net/ to release/iMouse2/ and relaunch. Build to the staging folder, test there, deploy only when green: the app locks its own files while running. The SDK is at C:\Program Files\dotnet\dotnet.exe.

Open

What's left

Docs README and TESTING.md are badly stale

They describe an app from several iterations ago — "1, 2, or 5 frames per second", "40 checks", "17 interaction checks", an older UI. Misleading as written. Worth a rewrite; deliberately not done unasked.

Unanswered Two questions put to the user

Whether to add the rest of the vendor's vertical strip (Restart, Lock, Ctrl Bar, KB, Cast, App, IME, Disc) — currently only Reset and Home. And whether the device-list checkbox reads clearly as "select mirror followers".

Unverified Two things never proven

Whether Reset actually corrects a drifted pointer — confirmed only that it clears the stuck-click state and returns code 0 everywhere. And whether the wall holds up with a real rack of 10+; only two phones were ever attached, so the aggregate floor (period = max(tilePeriod, tiles × 12 ms)) is untested at scale.

Blocked Full independence from IMService.exe

The vendor HID report format. The descriptor is vendor-defined and the 9-byte layout is opaque; decoding it needs a USB capture (USBPcap / Wireshark) of known actions. Re-implementing the AirPlay receiver would also be required. Neither blocks console work — the documented API covers video and every input.

Minor: the search box has no placeholder; the group filter is Visibility="Collapsed".

Handling

Care required

Credential in the vendor config

C:\iMouseXP\IMService.json stores the account password as trivially reversible hex obfuscation — recoverable from that file alone. Do not print it, do not carry the scheme forward, and keep build/ excluded by .gitignore.

Don't resize the vendor console during capture tests

Repeatedly minimising and resizing it left it rendering black and unable to recover; it needed restarting. The kernel was untouched, but avoid the situation.

This project is not a git repository. And never point the app's write paths at release/iMouse2/ while it is running.
